## Context

The template currently renders every CI step into every consumer. The 0.7.0 publish-job port proved the cost model: shared logic diverges silently per consumer and fixes roll out one `copier update` at a time. Python-project-common (same fleet, same operator) runs thin callers against versioned cross-repo workflows; the Rust template should follow the proven pattern rather than invent a second one.

## Goals / Non-Goals

**Goals:**

- One definition for each gate; fixes land fleet-wide without per-consumer merges.
- Versioning that makes rollout boring: immutable per-change tags, floating major default, major bump on breakage.
- Local hooks keep working exactly as specified today; CI stops invoking the hook runner and runs the same commands as explicit steps instead.

**Non-Goals:**

- No publish logic moves remote (sensitive, per Advisor and per Python precedent).
- No secrets in test workflows, no token forwarding design.
- No private-repo support matrix (fleet is verified public; if that ever changes, authentication is a new change).

## Decisions

### 1. One reusable file, profile-parameterized, explicit steps

`xrepo--tester.yaml` lives at the repository root (cross-repo `uses:` requires a repo-root path, so it cannot live under `template/`); it is template-maintained infrastructure, versioned by the same git tags. Inputs are `platforms` (JSON array of {os, cpu, runner, target} objects, bound at each call site to the initializer's `platforms` output), `cargo-profile` (validated string, `dev` or `release` — Cargo's own profile names, so no `debug` variant exists to choose — where a leading validation step rejects anything else), and `has-library` (boolean, rendered from the consumer's crate shape, deciding whether doctest steps run; a boolean suffices because the only shape-dependent CI behavior is doctests, and any future executable-specific gate would revisit this as a new input). Jobs chain lint into build into test, all fanning out as a build matrix over the platforms so every gate compiles and lints natively. Lint runs clippy, rustfmt `--check`, and linecheck on every profile — native per-platform execution, because `cfg`-gated code makes clippy results platform-dependent and no single-runner shortcut survives that. Build compiles `--all-targets`; test runs nextest plus doctests with per-profile flags spelled out explicitly — no pre-commit invocation in CI, no pasted `--profile` flag, preserving the dev/test semantic distinction Advisor required. The objects are deliberately denormalized: `runner` and `target` are pure functions of (`os`, `cpu`) computed once in the initializer, so the mapping lives in exactly one place and consumers — including consumer-authored custom workflows, which the template never rewrites — never carry lookup tables.

### 2. Both profiles run in tester, in parallel

The tester calls the reusable twice — dev for fast feedback on every PR, release so release-only breakage surfaces on PRs, not first at tag time. Cost is accepted explicitly: roughly double test minutes per PR in exchange for killing the "green PR, red release" class. Releaser still calls the release profile on tags (the gate before publish must run on the tag ref, not on some earlier PR state), plus local package and publish jobs.

### 3. Custom testers declare the same contract, normatively

`local--tester.yaml` MUST declare at least the two typed inputs — `platforms` (string carrying a JSON-encoded array of {os, cpu, runner, target} objects, bound from the initializer's `platforms` output) and `cargo-profile` (string; the caller passes `dev` or `release` and the callee validates it) — when it is called; any additional callee inputs MUST be non-required (have defaults) by the template's `custom` job; the call passes the full array per invocation and the called workflow fans out internally. `has-library` is deliberately absent from this contract: the shared workflow is generic and must be told the crate shape, while the custom author knows their own crate and encodes library-ness directly — there is nothing to pass. The same holds on the release side: `local--releaser.yaml` MUST declare the same two typed inputs, and the template's `custom-release` job passes them the same way with explicit `contents: read`, no secrets, and no `has-library`, with publish and binary jobs waiting on it. A consumer file MAY declare additional inputs only with defaults, since the template caller passes exactly the shared pair. Existing consumer files that accepted no inputs predate this contract; they are preserved byte-identical by `_skip_if_exists` and MUST be migrated deliberately (add the declared inputs), because passing undeclared inputs fails workflow resolution — there is no silent fallback. The template's custom callers use job-level `uses:` with explicit `contents: read`, no secrets, and no `has-library` on either call; consumer callees run under that token.

### 4. Stub files are rendered; caller jobs are the gated part

`local--tester.yaml` and `local--releaser.yaml` stubs render unconditionally as starting points, both `_skip_if_exists`-protected so consumer implementations are never overwritten. Rendering unconditionally (rather than omitting when disabled) is a deliberate choice: it gives every consumer a starting file to fill in, instead of a missing file whose resolution failure carries no guidance. Every stub fails loudly with implementation instructions until replaced — a missing or unimplemented gate reads as red, never green, which is also why the template never auto-generates a passing stub and never wires `secrets: inherit`.

### 5. Versioning: immutable minors, floating major, consumer pins floating

Every change cuts `@gha-X.Y` (immutable, audit point); the floating major advances with it; consumers pin the floating major by default and only pin exact minors for forensics or freeze windows. Breaking changes start `@gha-<next-N>` and are announced as such. This is the operator's decision: maintainability over per-consumer gating, with the discipline (backward compatibility + major bumps) as the blast-radius control. Template CI plus required checks on this repo are the pre-merge gate for shared changes. Before any tag moves, dedicated template-owned fixture caller branches (`fixture/promotion-lib`, `fixture/promotion-bin`, `fixture/promotion-red`) each call the literal hosted ref `emcd/rust-project-common/.github/workflows/xrepo--tester.yaml@<candidate-sha>` with the candidate SHA pinned. Callers MUST live on revisions other than the candidate: a committed fixture cannot name its own commit, and job-level `uses:` takes no expressions. Jobs in the called workflow check out the caller repository at the caller ref while the template root has no Cargo.toml, so each caller branch MUST hold a real rendered crate at its checkout root (library-bearing, binary-only, and deliberately gate-violating respectively; the red branch also hosts the bogus-profile dispatch for the validation control). Lib and bin callers run dev and release and MUST be green; red MUST fail in the gate step and bogus-profile in the leading validation step — never in resolution or checkout. The same-commit local-call alternative is rejected: it tests the worktree rather than an immutable candidate, and per-job fixture staging would need contract changes the proposal avoids. Fixture branches are created once with operator approval and their candidate SHAs advanced per candidate by the operator-owned promotion process. The floating major never advances on unexecuted or unexpected-verdict candidates; first tag and all moves remain operator-owned. Shared workflow files change only through reviewed commits, and tags move only through the operator-owned promotion process with tag creation, update, and deletion restricted to it. Published immutable tags never move. Promotion rechecks evidence freshness (exact candidate SHA, fixture caller revisions, current tag/main eligibility) so stale receipts cannot promote. Recovery means rolling the floating major back to a retained immutable pin: operator-authorized, fixture-green for that pin, never an arbitrary retarget.

### 6. Initializer stays local; pre-commit leaves CI

The initializer is answers-rendered (OS/CPU matrix), so it cannot move remote — same split as Python. Its `cells` output is renamed to `platforms` in the same motion (task 1.6); re-pin already rewrites every rendered caller; consumer-owned readers migrate by hand as specified. Local hooks are untouched: the hook config stays the local fast path (lint plus unit tests on pre-commit, release twins on pre-push). What changes is CI only: testers and the release gate stop invoking the pre-commit runner and run the same commands as explicit steps instead. The old parity architecture (same invocation, both sides) retires, deliberately, because it could not express the lint → build → test prerequisite chain or per-platform legible failure. In its place: an explicit hook-ID ↔ CI-step mapping with normalization (lockfile-bootstrap wrappers stripped), an allowlist for steps with no hook twin (dev builds, setup and toolchain install, lockfile generation, packaging, attestation, artifact up/download, release create/upload), and a copiertv check that fails validation on any unmapped drift in either direction. The pre-push release twins keep covering the local side exactly as specified today.

### 7. One umbrella gate on the tester; needs edges on the releaser

Required status checks need stable names; per-platform jobs produce per-platform contexts that multiply with every platform answer. The tester gets a single `final-gate` job: `needs` on all gate jobs *including* the custom job whenever the answer renders it, `if: always()`, failing unless every needed result is `success`. Branch protection targets `final-gate` only. No releaser umbrella: tag-triggered runs are not PR-required checks, so the release chain relies on needs edges instead of a verdict job — release gates feed a per-platform `package` job that runs regardless of custom CI, dry-run, or publication flags, and `publish-crates-io` plus `build-binaries` wait on the full needs set (whole-`platforms` release success, `package` success, and `custom-release` success when rendered) while keeping tag/dry-run/publication predicates and credential protections; `publish-github` follows transitively via `build-binaries`, unconditionally whenever the publisher exists. This is what makes either required-checks path (settings app or per-repo API) maintainable, and the tester verdict is valuable even if neither path is ever built, because humans reading checks see one verdict per PR.

### 8. Least-privilege execution authority

Every cross-repo `uses:` call (dev, release, release-gates, custom, custom-release) declares explicit `permissions: contents: read` or less; the shared callee requires no more than `contents: read`, accepts no secrets, and receives the caller token through downgrade-only inheritance. Local `package` and `hygiene` jobs run least-privilege, and checkouts that never push set `persist-credentials: false`. Write and OIDC privileges stay confined to the existing local publisher jobs; nothing else gains them. The template sets every permissions block explicitly and never relies on consumer repo-default token permissions. The tester triggers on `pull_request`, never on privileged `pull_request_target` execution of PR code. `platforms` entries are validated against the supported GitHub-hosted runner/target mapping pinned alongside the shared workflow (initializer tables and callee allowlist MUST agree) before fan-out, and input values travel via `env:`, never interpolated into shell source.

## Risks / Trade-offs

- [Fleet-wide breakage from one bad push] → Accepted explicitly by the operator as the price of instant rollout; mitigated by backward-compat discipline, major-bump rule, template-repo CI plus required checks, and canary order (cistella, approots, then fleet).
- [Tester runs ~2x test minutes, plus native lint per platform] → Accepted: the parallel release track is the point (catch release-only breakage at PR time), and per-platform lint is the cost of honest platform coverage. Pre-push hooks keep covering the local side.
- [Platforms inputs must stay compatible] → Mitigation: the `platforms` JSON schema (os, cpu, runner, target), bound from the initializer's `platforms` output, is pinned by the same contract as today; changing it is a breaking change under the versioning rule.
- [`custom` contracts need a shared fan-out shape] → Both caller jobs pass the full inputs and the called workflow fans out internally; single-runner custom workflows keep working by ignoring all but one platform, and the contract documents the shape. Existing no-input files are preserved and migrate deliberately.
- [Hygiene checks need a home without pre-commit in CI] → A dedicated `hygiene` job runs the file-hygiene hook IDs via a pinned pre-commit tool: one `pre-commit run <id>` invocation per ID taken from the template's own pre-commit config (single source of truth, not a parallel list), with the rendered config path, `--hook-stage pre-commit`, and `--all-files`, failing on any invocation failure (unknown ID, hook failure, or fixer rewrite). This is the single sanctioned exception to "no pre-commit in CI" wherever that rule is stated: the alternative is reimplementing file checks as shell, which is worse in every dimension.
- [Skip propagation must not silently pass] → The DAG has no conditional jobs: lint always runs (both profiles), build needs lint, test needs build, the tester `custom` job needs only `initialize`, and the releaser `custom-release` job needs only `initialize`. No `if:` guards on any mandatory gate job in the shared or generated paths — publication predicates keep theirs — so no job is ever present-but-skipped. Failure or cancellation upstream can still skip downstream jobs; the umbrella's deliberate `if: always()` exists precisely to convert those skips into inspected results: `final-gate` fails unless every needed result is `success`. The hygiene job is unconditional.
- [Existing no-input custom files break] → Mitigation: they are preserved byte-identical by `_skip_if_exists`; migration (add the declared inputs) is an explicit consumer task at re-pin, announced with the change, not a silent failure at 2 AM. Copier rewrites rendered callers, but consumer-owned files that read `needs.initialize.outputs.cells` are not rewritten; their owners MUST rebind to `needs.initialize.outputs.platforms` by hand at re-pin.
